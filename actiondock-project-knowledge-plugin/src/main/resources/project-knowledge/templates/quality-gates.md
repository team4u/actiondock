# 质量门槛

在写入任何正式文档前逐项做语义审查。这里关注内容质量、证据绑定和外部证据吸收结果，不依赖单独的校验脚本。

## 事实和证据

- 只描述当前代码、配置、数据结构和文档能证明的状态。
- 每个重要结论都要绑定至少一种证据：文件路径、类/函数/方法/接口名、配置键、表名、字段名、索引名、OpenAPI/DDL/CI 明确条目。
- 有限推断必须说明依据和不确定性。
- 证据不足时写入报告，不生成伪完整正文。

## 文档深度

- 不生成只有清单或几行摘要的浅文档。
- `ACTIONDOCK.md` 只导航，不复制深度正文。
- 每篇主题文档都要解释至少一条调用链、数据关系、配置影响或诊断路径，而不是只列文件。
- 正式文档不得引用 `.knowledge-tmp/` 或要求读者查看临时产物。
- 不保留明显占位符、空标题、纯模板片段或无吸收结果的外部证据摘抄。

## 流程质量

- 流程粒度固定为端到端业务用例；不能用接口摘要替代流程文档。
- 每篇流程文档都要覆盖触发、输入校验、主链路、关键分支、状态变化、数据读写、事务/幂等、外部依赖、日志错误和证据缺口。
- 如果只能写出几行说明，说明追踪不足；继续追代码。若证据仍不足，回退为跳过项并写明原因。
- 发现显式校验、异常分支、唯一约束、时间窗口或权限判断时，补充业务规则文档。
- 发现核心状态枚举和迁移逻辑时，补充状态机文档并从流程正文链接过去。

## 数据语义和 SQL 可用性

- 完整 DDL 存在时，数据表文档必须覆盖全部表结构，而不是只挑核心表。
- 结构信息和业务语义都要可用于后续编写 SQL：字段、约束、索引、状态/枚举取值、读写关系和常见风险不能缺位。
- DDL 注释只能作为弱语义参考；表职责、字段含义、状态迁移和诊断价值必须优先引用当前代码、日志或测试。
- 无法确认业务语义时，明确写“语义证据不足”，并说明缺少哪类代码证据。
- 代码与 DDL 冲突时以代码为准，同时记录冲突。

## 诊断和运行知识

- 诊断文档必须可操作，能回答“何时查、查什么、怎么看结果、接下来做什么”。
- SQL 和日志手册按场景组织；不要堆查询语句列表。
- runbook 只负责组合排查路径；工具必填参数和通用上下文留在 `docs/agent/tool-context.md`。
- 外部依赖、任务补偿和手动操作文档都要说明触发条件、风险、失败处理和证据来源。
- 查询工具上下文只能来自真实证据；缺失字段写影响，不填占位值。
- `evidenceFiles` 中无法可靠解析、无法归类或与代码冲突的内容，只能进入报告，不能原样抄进正式正文。
- `evidenceFiles` 不要求统一格式，但最终必须能说明哪些内容被吸收、吸收到哪里、哪些内容被跳过，以及跳过原因。

## Refresh 校验

- 已有文档引用的路径、类、函数、表和字段若不存在，必须标记为过期并更新或写入更新报告。
- 只更新受影响文档；不要为了统一模板重写已有高质量人工内容。
- 新增入口、流程、表、字段、状态枚举、错误码或外部依赖必须进入对应索引或报告。
- 代码与已有文档冲突时，以当前代码为准，并记录冲突来源。

## 最终审查

- 输出语言与用户要求一致，术语前后一致。
- 所有重要结论都能回指到当前仓库中的证据或用户提供的材料。
- 报告中显式列出跳过项、冲突项、语义证据不足项和需人工审查项。
- 报告中按来源显式列出 `evidenceFiles` 的吸收情况：吸收到哪些文档、哪些内容被跳过、跳过或冲突原因是什么。
