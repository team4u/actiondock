# ActionDock：把脚本变成可复用的工具资产

很多自动化一开始都只是一个脚本。

它可能用来清理临时文件、同步数据、生成报表、检查服务状态，或者调用某个内部系统。只要能跑通，当时就够了。

真正的问题通常出现在它开始变得有用之后。

脚本被复制到服务器、CI、项目目录和文档里；参数改了，调用方没同步；依赖升级了，旧副本还在跑；出问题时，也很难知道是谁在什么时候、用什么输入执行过。后来，它可能还会被定时任务、Webhook、其他脚本，甚至 AI Agent 调用。这个时候，脚本就不再只是一个临时命令，而是变成了一块隐形的基础设施。

ActionDock 解决的就是这个阶段的问题：把脚本从一段散落的源码，整理成有身份、有 Schema、有版本、有依赖、有执行记录，并且可以被 CLI、API、Webhook、定时任务和 AI Agent 稳定调用的工具资产。

---

## 脚本不缺，缺的是长期复用的约定

脚本本身并不稀缺。开发者、运维、平台工程师每天都会写脚本。

真正麻烦的是脚本后面的事：

* 别人怎么调用？
* 参数怎么传？
* 哪些字段是必填？
* 输出结果是什么结构？
* 依赖哪些环境、配置、插件或外部服务？
* 哪个版本可以放心用于生产？
* 谁执行过？
* 失败时日志在哪里？
* AI Agent 能不能安全地调用它？

这些问题如果靠文档、口头约定或复制粘贴来解决，时间一长就会失控。

ActionDock 的核心思路很简单：脚本仍然用代码写，但它不再只是一段源码。它会被平台封装成一个可管理、可发布、可分发、可审计的工具资产。

---

## ActionDock 是什么

ActionDock 是一个面向开发者的脚本资产化平台。

它的目标不是教你怎么写脚本，而是解决脚本写完之后如何长期使用的问题：如何定义输入输出、如何发布稳定版本、如何复用已有能力、如何跨环境执行、如何记录执行过程、如何让 AI Agent 在受控范围内调用内部工具。

你可以先把它当成自己的脚本管理和自动化入口。随着使用范围扩大，它也可以继续承接团队协作、多节点管理、仓库分发、配置隔离、权限治理和 AI 工具化这些需求。

更具体地说，ActionDock 适合这些场景：

* 你有很多脚本，但它们散落在不同机器和项目目录里。
* 你希望脚本不只是能运行，还能被稳定调用。
* 你需要 CLI、管理台、API、定时任务和 Webhook 共用同一套参数定义。
* 你希望脚本有草稿、发布、版本和执行记录。
* 你需要把内部能力暴露给 AI Agent，但不希望 Agent 靠 Prompt 猜参数。
* 你希望把常用脚本、插件、配置模板和 Skills 打包成可分发的工具库。

它不适合所有自动化场景。

如果只是一次性命令，或者业务人员想用拖拽节点快速搭一个简单流程，n8n、Dify、扣子这类可视化工具可能更合适。ActionDock 更适合那些最终会沉淀为长期工具、需要多人复用、版本管理、执行审计、环境隔离，甚至要暴露给 AI Agent 调用的脚本型自动化。

## 一个脚本如何变成工具资产

脚本一旦要被复用，只有源码是不够的。

源码能说明“它做了什么”，但很难完整说明“它是谁、怎么调用、依赖什么、哪个版本可以放心用”。

在 ActionDock 中，脚本会被整理成一个 `ScriptDefinition`。它包含脚本 ID、名称、类型、源码、输入输出 Schema、依赖声明和发布快照。

一个简化示例：

```json
{
  "id": "hello-groovy",
  "name": "Hello Groovy",
  "type": "GROOVY",
  "source": "def name = input.name ?: \"World\"\nreturn [message: \"Hello, \" + name + \"!\", upperName: name.toUpperCase()]",
  "inputSchema": {
    "type": "object",
    "properties": {
      "name": {
        "type": "string",
        "title": "Name"
      }
    }
  },
  "outputSchema": {
    "type": "object",
    "properties": {
      "message": {
        "type": "string",
        "title": "Message"
      },
      "upperName": {
        "type": "string",
        "title": "Upper Name"
      }
    }
  }
}
```

这里最重要的是 `inputSchema` 和 `outputSchema`。

它们不是只给人看的文档，而是平台运行时会使用的结构化契约。CLI 会基于它解析参数，管理台会基于它生成表单，REST API 会基于它统一输入输出，AI Agent 会基于它理解工具参数，执行引擎也会基于它在运行前做校验。

这样，脚本就从“能跑的一段代码”变成了“可被稳定调用的工具”。

---

## 一份 Schema，连接多个入口

脚本被更多入口调用时，最容易乱的是参数。

CLI 写一套说明，管理台写一套表单，REST API 写一套文档，AI Agent 的 Prompt 里再补一套工具描述，时间一长就会不一致。

ActionDock 把参数约定收进 Schema。脚本只维护一份输入输出契约，多个入口都基于这份 Schema 工作。

同一个脚本，可以在 CLI 中这样调用：

```bash
actiondock script run hello-groovy --name alice --json
```

也可以通过 REST API 调用：

```bash
curl -X POST http://localhost:5177/api/scripts/hello-groovy/execute \
  -H 'Content-Type: application/json' \
  -d '{"input":{"name":"alice"},"mode":"SYNC"}'
```

也可以在管理台里通过自动生成的表单执行。

如果脚本用于定时任务，平台会保存脚本 ID、Cron 表达式和固定输入；如果脚本用于 Webhook，外部事件会经过标准化、过滤、幂等检查和输入映射，再提交给目标脚本执行；如果脚本要暴露给 AI Agent，Schema 会直接变成工具输入结构，减少模型猜错参数的风险。

入口可以变多，但参数规则不用复制多份。

## 从临时脚本到稳定工具

很多脚本一开始只是临时任务，可以随手改。

但一旦它被定时任务、Webhook、AI Agent 或其他脚本调用，随手改源码就会变成风险。你可能只是想调试一个字段，但线上流程已经开始跑这份改动。

ActionDock 把脚本分成草稿和发布两个状态。

草稿用于开发和调试。发布后，平台会生成稳定快照。真正被定时任务、脚本互调、Webhook 和 AI 工具调用时，应当尽量使用发布版本，避免草稿改动意外影响稳定流程。

这让脚本可以像一个小型工具一样演进：

开发时有试错空间，运行时有稳定边界；需要回退时，也可以回到上一个发布状态。

## 复杂能力如何复用

真实的自动化流程很少只适合一种语言。

流程编排、系统操作可能更适合 Groovy；数据处理、爬取、文本处理又更适合 Python。没有统一运行时的时候，跨语言协作往往要拆成服务、HTTP 接口，或者写一堆临时命令。

ActionDock 允许 Groovy 调 Python，也允许 Python 反向调用 Groovy 脚本。

脚本执行时，平台会注入一组运行时对象：

| 对象        | 作用        |
| --------- | --------- |
| `scripts` | 调用其他已发布脚本 |
| `state`   | 读写共享状态    |
| `config`  | 读取全局配置值   |
| `log`     | 写入执行日志    |

例如在 Groovy 中调用另一个脚本：

```groovy
def result = scripts.invoke("python-data-processor", [input: rawData])
```

在 Python 中也可以反向调用 Groovy 脚本：

```python
report = scripts.invoke("groovy-report-generator", {"data": processed})
```

这样，团队可以用合适的语言处理合适的问题，而不需要为了跨语言调用额外维护一层微服务。

脚本适合表达流程，但不是所有能力都适合长期写在脚本里。内部 SDK、专有系统接入、统一鉴权、复杂客户端封装这类能力，如果每个脚本都写一遍，很快会变成另一种复制。

因此 ActionDock 也提供插件机制。

插件基于 PF4J，打成 JAR 安装到平台里，通过统一方式调用：

```groovy
def result = plugins.invoke("my-plugin", "hello", [name: "world"])
```

脚本负责流程编排，插件负责沉淀稳定底层能力。对脚本作者来说，底层能力到底来自 Groovy、Python 还是 Java 插件并不重要；重要的是，平台里的能力都能按同一种方式调用。

## 配置、状态和环境隔离

脚本放到长期运行的环境后，真正容易失控的往往不是代码，而是环境。

哪个节点连哪个地址？谁在用哪套密钥？仓库更新后，本地覆盖值会不会被冲掉？这些内容都不适合硬编码在脚本里。

ActionDock 把环境信息集中到配置层。脚本和插件通过 `config.get()` 或 `${config.key}` 引用配置，敏感值标记为 Secret 后会在管理台和接口中脱敏。

仓库分发的工具也可以带配置模板。安装后，模板同步成受管配置；本地环境可以复制为本地覆盖值，仓库更新时保留本地差异。

对于 dev、test、prod 使用不同密钥、地址和策略的场景，这种隔离会明显降低维护成本。

## 执行记录让自动化可追踪

自动化越有用，越需要知道它到底做过什么。

脚本被人手动执行、被定时任务触发、被 Webhook 调用、被 AI Agent 使用以后，如果没有统一记录，排查问题只能靠猜。

ActionDock 会保存执行输入、输出、状态、日志和错误详情。外部事件进入平台后，也会保存事件记录、标准化结果和触发器派发结果。

同时，平台还提供访问令牌、配置值、共享状态和数据备份能力：

* CLI、CI 或外部系统可以使用 Bearer Token 调用平台。
* 配置和 Secret 可以集中管理。
* 跨脚本共享状态可以设置过期时间和敏感值标记。
* 管理台可以导出和恢复系统数据包，用于升级前备份、环境迁移和故障恢复。

这些能力不会让脚本本身更复杂，但会让脚本进入长期运行环境后更稳。

## 仓库分发：让工具可以被发现、安装和更新

工具变多后，真正麻烦的不是“有没有”，而是“别人怎么发现、怎么安装、怎么更新、怎么知道自己装的是不是同一版”。

ActionDock 的 Repository 机制用于解决这个问题。

仓库里可以放脚本工具、插件、事件源资产、AI 能力包和 Skills。仓库可以来自 Git、HTTP 或本地目录。同步后，用户可以从管理台或 CLI 发现、安装和更新这些资产。

仓库资产不只包含源码，还可以带上依赖、调度模板和配置模板。安装时可以选择是否连同依赖一起安装，避免“脚本装好了，环境还缺一堆东西”。

仓库也支持工作副本与上游同步。仓库里的工具和事件源资产可以创建为本地工作副本，平台会通过上游绑定记录来源、版本、路径、提交和摘要，并判断当前状态是已同步、本地有改动、远端有改动，还是两边同时改动。

这使得团队可以在平台里直接编辑和调试本地工作副本，同时保留与仓库上游的同步关系和更新通道。

## AI Agent 如何安全调用内部工具

AI Agent 调内部工具时，最怕两件事。

第一，工具参数只写在 Prompt 里，模型只能猜。

第二，Skill、工具、执行权限和审计混在一起，后面很难治理。

ActionDock 的 AI 接入重点不是让 Agent 自由执行脚本，而是把已发布脚本作为受控工具暴露给 Agent。

在 ActionDock 中，Agent Profile 由几类内容组成：

* Model Profile：使用哪个模型、哪个供应商、什么 API Key。
* Toolset / Direct Tools：Agent 能调用哪些工具。
* Skills：Agent 具备哪些任务知识、流程约束和使用说明。

已发布的 `TOOL` 类型脚本会暴露为 ActionDock AI 工具，工具名是 `script.<scriptId>`。脚本的 `inputSchema` 会直接变成工具输入结构，Agent 不需要靠 Prompt 猜参数。

Skill 则是另一层。它不是执行入口，更像是 Agent 的知识包：告诉 Agent 某类任务的背景、流程、边界和工具使用方式。

例如要做一个告警分诊 Agent：

* `send-message`、`query-oncall`、`create-ticket` 这些脚本发布后，加入 `incident-tools` Toolset。
* `incident-triage` Skill 说明告警如何判断等级、什么时候升级、信息如何整理。
* Agent Profile 绑定这个 Toolset 和 Skill。

处理告警时，Skill 管判断和流程，工具脚本管实际操作。每一次工具调用都会进入 ActionDock 的执行记录。

这才是 AI 接入内部工具时更重要的部分：不是让 AI 什么都能做，而是让它在已经定义好的工具、权限和审计边界里做事。

## 与拖拽式工作流工具的区别

n8n、Dify、扣子这类拖拽式工具很适合快速把几个现成节点串起来，也适合非技术人员配置简单流程。它们的优势是直观，上手快，适合验证想法。

但很多自动化流程一开始很简单，后面会慢慢变复杂：条件分支越来越多，异常处理越来越细，依赖要复用，配置要区分环境，还要考虑版本、审计和代码评审。

这时继续在画布里堆节点，维护成本会逐渐上来。

ActionDock 的定位不同。它面向的是开发、运维、平台这类更习惯用代码表达逻辑的人，所以它的基础不是画布，而是脚本、Schema、插件和发布快照。

拖拽式平台复用的是节点；ActionDock 复用的是脚本和插件。

脚本适合沉淀流程步骤、业务动作和编排逻辑。插件适合沉淀内部 SDK、系统接入和稳定底层能力。

| 场景          | 拖拽式工作流       | ActionDock       |
| ----------- | ------------ | ---------------- |
| 主要使用者       | 非技术人员、业务配置人员 | 开发、运维、平台人员       |
| 基础表达方式      | 画布和节点        | 脚本、Schema、插件     |
| 复用单元        | 节点           | 脚本和插件            |
| 复杂逻辑        | 画布容易变重       | 用代码表达            |
| 版本、审计、分发    | 依赖平台能力       | 围绕脚本资产内建         |
| AI Agent 调用 | 通常需要再整理工具描述  | 直接基于 Schema 暴露工具 |

所以 ActionDock 不是要替代所有可视化编排工具，而是把那些最终会变成脚本、服务或内部工具的流程，放进一套更贴近开发者工作方式的工程体系里。

## 快速开始

安装并启动：

```bash
npm install -g actiondock
actiondock server
```

启动后访问：

```text
http://localhost:5177/admin/app/scripts
```

运行一个内置示例：

```bash
actiondock script run hello-groovy --name alice --json
```

成功后会看到类似结果：

```json
{
  "status": "SUCCESS",
  "output": {
    "message": "Hello, alice!",
    "upperName": "ALICE"
  }
}
```

接下来可以继续尝试：

* 创建一个常用脚本，补充输入输出 Schema。
* 分别用 CLI 和管理台执行它。
* 发布脚本，生成稳定快照。
* 为脚本添加定时任务。
* 配置不同环境的 CLI profile。
* 把脚本发布到仓库，供其他人发现、安装和更新。

---

## 总结

ActionDock 解决的不是“怎么写脚本”，而是“怎么让脚本长期可用、可复用、可治理”。

它把脚本整理成有身份、有 Schema、有版本、有依赖、有配置、有执行记录的工具资产，并让这些资产可以被 CLI、管理台、REST API、定时任务、Webhook、其他脚本和 AI Agent 稳定调用。

对个人来说，它可以先是一个统一的脚本管理和自动化入口。

对团队来说，它可以继续承接脚本分发、环境隔离、执行审计、插件复用、仓库管理和 AI 工具化。

脚本不缺。真正缺的是让脚本长期可靠运行的工程体系。

ActionDock 想补上的，就是这一层。
