# ActionDock：把脚本变成可复用的工具资产

很多自动化一开始都只是一个脚本。

可能用来清理临时文件、同步数据、生成报表、检查服务状态，或者调用某个内部系统。能跑通就够了。

真正的问题出现在它开始变得有用之后。

脚本被复制到服务器、CI、项目目录和文档里；参数改了，调用方没同步；依赖升级了，旧副本还在跑；出问题时，很难知道是谁在什么时候、用什么输入执行过。后来，它可能还会被定时任务、Webhook、其他脚本，甚至 AI Agent 调用。这个时候，脚本就不再只是一个临时命令，而是变成了一块隐形的基础设施。

ActionDock 要解决的就是这个阶段的问题：把脚本从散落的源码，整理成有身份、有 Schema、有版本、有依赖、有执行记录，并且可以被 CLI、API、Webhook、定时任务和 AI Agent 稳定调用的工具资产。

---

## 脚本不缺，缺的是长期复用的约定

脚本本身不稀缺。开发者、运维、平台工程师每天都在写。

麻烦的是脚本后面的事：

* 别人怎么调用？
* 参数怎么传？
* 哪些字段必填？
* 输出什么结构？
* 依赖哪些环境、配置、插件或外部服务？
* 哪个版本能放心用于生产？
* 谁执行过？
* 失败时日志在哪？
* AI Agent 能不能安全地调用它？

靠文档、口头约定或复制粘贴来解决，时间一长就会失控。

ActionDock 的思路很简单：脚本还是用代码写，但它不再只是一段源码。它会被平台封装成一个可管理、可发布、可分发、可审计的工具资产。

---

## ActionDock 是什么

ActionDock 是一个面向开发者的脚本资产化平台。

它的目标不是教你怎么写一次脚本，而是解决脚本变得有用之后的长期问题：怎么定义输入输出、怎么发布稳定版本、怎么复用已有能力、怎么跨环境执行、怎么记录执行过程、怎么让 AI 和 Agent 在受控范围内使用这些内部工具。

你可以先把它当成自己的脚本管理和自动化入口。用的人多了，它也可以承接团队协作、多节点管理、仓库分发、环境隔离、权限治理和 AI 工具化这些需求。

具体来说，ActionDock 适合这些场景：

* 脚本散落在不同机器和项目目录里，想统一管起来。
* 不只是让脚本能运行，还想让它能被稳定调用。
* 希望 CLI、管理台、API、定时任务和 Webhook 共用同一套参数定义。
* 想让脚本有草稿、发布、版本和执行记录。
* 要让 AI 直接调用已有脚本，但不想为每个脚本手写 Skill 或 Prompt。
* 希望脚本本身也能直接使用大模型，而不是每个脚本都单独接 AI API。
* 想把常用脚本、插件、配置模板和 Skills 打包成可分发的工具库。

当然，它不是所有场景都适用。

如果只是一次性命令，或者业务人员想用拖拽节点快速搭一个简单流程，n8n、Dify、扣子这类可视化工具可能更合适。ActionDock 适合那些最终会沉淀为长期工具、需要多人复用、版本管理、执行审计、环境隔离，甚至要进入 AI 工作流的脚本型自动化。

## 源码不是工具，契约才是工具

脚本要被复用，只有源码是不够的。

源码能说明"它做了什么"，但很难说清楚"它是谁、怎么调用、依赖什么、哪个版本可以放心用"。

一段代码可以跑，不代表它已经是工具。平台不知道怎么校验它的输入，管理台不知道怎么生成表单，CLI 不知道怎么把参数映射进去，AI 也不知道哪些字段能填、哪些字段必须填。

在 ActionDock 中，脚本会被整理成一个 `ScriptDefinition`。它包含脚本 ID、名称、类型、源码、输入输出 Schema、依赖声明和发布快照。

一个简化示例：

```json
{
  "id": "hello-groovy",
  "name": "Hello Groovy",
  "type": "GROOVY",
  "source": "def name = input.name ?: \"World\"\nreturn [message: \"Hello, \" + name + \"!\", upperName: name.toUpperCase()]",
  "inputSchema": {
    "type": "object",
    "properties": {
      "name": {
        "type": "string",
        "title": "Name"
      }
    }
  },
  "outputSchema": {
    "type": "object",
    "properties": {
      "message": {
        "type": "string",
        "title": "Message"
      },
      "upperName": {
        "type": "string",
        "title": "Upper Name"
      }
    }
  }
}
```

最重要的是 `inputSchema` 和 `outputSchema`。

它们不是给人类看的文档，而是平台运行时会用的结构化契约。CLI 基于它解析参数，管理台基于它生成表单，REST API 基于它统一输入输出，AI Agent 基于它理解工具参数，执行引擎基于它在运行前做校验。

这样，脚本就不再只是"能跑的一段代码"，而是变成了有身份、有契约、有发布边界、能被多个入口稳定调用的工具资产。

---

## 参数只写一次，所有入口都能用

脚本被更多入口调用时，最容易乱的是参数。

CLI 写一套说明，管理台写一套表单，REST API 写一套文档，AI Agent 的 Prompt 里再补一套工具描述，时间一长就会不一致。

真正麻烦的不是多写几行文档，而是这些说明迟早会分叉。脚本参数已经改了，CLI 文档没改；表单还在展示旧字段；Prompt 里还写着旧调用方式。最后不是某个入口坏了，而是所有入口都在用不同版本的"真相"。

ActionDock 把参数约定收进 Schema。脚本只维护一份输入输出契约，多个入口都基于这份 Schema 工作。

同一个脚本，在 CLI 中可以这样调用：

```bash
actiondock script run hello-groovy --name alice --json
```

也可以通过 REST API 调用：

```bash
curl -X POST http://localhost:5177/api/scripts/hello-groovy/execute \
  -H 'Content-Type: application/json' \
  -d '{"input":{"name":"alice"},"mode":"SYNC"}'
```

还可以在管理台里通过自动生成的表单执行。

如果脚本用于定时任务，平台会保存脚本 ID、Cron 表达式和固定输入；如果用于 Webhook，外部事件会经过标准化、过滤、幂等检查和输入映射，再提交给目标脚本执行；如果要暴露给 AI Agent，Schema 会直接变成工具输入结构，减少模型猜错参数的风险。

入口可以变多，参数规则不用复制多份。Schema 变成人、系统和 AI 共同理解脚本的语言。

---

## 脚本越有用，越不能随手改

很多脚本一开始只是临时任务，可以随手改。

但一旦它被定时任务、Webhook、AI Agent 或其他脚本调用，随手改源码就成了风险。可能只是想调试一个字段，但线上流程已经开始跑这份改动。

临时脚本可以快，稳定工具不能飘。越多人依赖它，越需要区分"正在改的版本"和"正在被调用的版本"。

ActionDock 把脚本分成草稿和发布两个状态。

草稿用于开发和调试。发布后，平台会生成稳定快照。定时任务、脚本互调、Webhook 和 AI 工具调用时，应该尽量用发布版本，避免草稿改动影响稳定流程。

这样脚本可以像小型工具一样演进：开发时可以快，运行时必须稳。需要回退时，也可以回到上一个发布状态。

## 不要把每个脚本都写成小系统

真实的自动化流程很少只适合一种语言。

流程编排、系统操作可能更适合 Groovy；数据处理、爬取、文本处理又更适合 Python。没有统一运行时的时候，跨语言协作往往要拆成服务、HTTP 接口，或者写一堆临时命令。

ActionDock 允许 Groovy 调 Python，也允许 Python 反向调用 Groovy 脚本。

脚本执行时，平台会注入一组运行时对象：

| 对象        | 作用        |
| --------- | --------- |
| `scripts` | 调用其他已发布脚本 |
| `state`   | 读写共享状态    |
| `config`  | 读取全局配置值   |
| `log`     | 写入执行日志    |

在 Groovy 中调用另一个脚本：

```groovy
def result = scripts.invoke("python-data-processor", [input: rawData])
```

在 Python 中反向调用 Groovy 脚本：

```python
report = scripts.invoke("groovy-report-generator", {"data": processed})
```

这样，团队可以用合适的语言处理合适的问题，不需要为了跨语言调用额外维护一层微服务。

脚本适合表达流程，但不是所有能力都适合写在脚本里。内部 SDK、专有系统接入、统一鉴权、复杂客户端封装这些，如果每个脚本都写一遍，很快会变成另一种复制。

脚本一多，最危险的不是代码量变大，而是每个脚本都开始自己处理鉴权、重试、客户端、配置和异常。最后每个脚本都像一个小系统，但没有小系统该有的边界。

ActionDock 也提供插件机制。

插件适合放那些不应该散落在脚本里的稳定能力。

比如内部系统 SDK、统一鉴权、数据库客户端、消息队列封装、专有协议、文件格式解析、加密签名、复杂重试策略，或者需要更高性能和更强类型约束的逻辑。这些能力如果放在脚本里，短期看很快，长期看会变成到处复制的基础设施。

插件把这些底层能力沉淀成平台扩展。脚本只需要调用一个动作，不需要知道底层怎么建连接、怎么签名、怎么处理重试、怎么兼容内部系统的细节。

插件基于 PF4J，打成 JAR 安装到平台里，通过统一方式调用：

```groovy
def result = plugins.invoke("my-plugin", "hello", [name: "world"])
```

脚本互调解决流程复用，插件解决底层能力复用。脚本负责流程编排，插件负责沉淀稳定 SDK、系统接入和统一鉴权。对脚本作者来说，底层能力来自 Groovy、Python 还是 Java 插件并不重要；重要的是，平台里的能力都能按同一种方式调用。

这也让团队协作更清晰：平台或基础设施团队可以维护插件，把复杂系统接入做成稳定动作；业务或运维同学用脚本编排这些动作，快速拼出自己的自动化流程。

插件也可以跟脚本一起进入仓库分发。一个工具包不只是几段源码，还可以包含脚本、插件、配置模板和依赖声明。安装时把底层能力和上层流程一起带上，避免"脚本装好了，真正能干活的 SDK 还没准备好"。

当这些脚本再暴露给 AI 或被内置 Skill 调用时，AI 看到的是清晰的脚本 Schema；真正复杂、敏感、需要稳定维护的系统接入，则留在插件里。这样既降低了脚本复杂度，也避免把内部 SDK 和鉴权细节暴露给每一次脚本编写。

## 真正容易出事的，往往不是代码

脚本放到长期运行的环境后，容易失控的往往不是代码，而是环境。

哪个节点连哪个地址？谁在用哪套密钥？仓库更新后，本地覆盖值会不会被冲掉？这些内容不适合硬编码在脚本里。

如果地址、密钥、环境差异都散在源码里，脚本迁移一次就要改一次，仓库更新一次就要核对一次。代码看起来没变，实际运行环境已经变了。

ActionDock 把环境信息集中到配置层。脚本和插件通过 `config.get()` 或 `${config.key}` 引用配置，敏感值标记为 Secret 后会在管理台和接口中脱敏。

仓库分发的工具也可以带配置模板。安装后，模板同步成受管配置；本地环境可以复制为本地覆盖值，仓库更新时保留本地差异。

对于 dev、test、prod 使用不同密钥、地址和策略的场景，这种隔离会明显降低维护成本。脚本不用到处改源码，也能在不同环境里按各自的配置运行。

## 自动化跑得越多，越不能靠猜

自动化越有用，越需要知道它到底做过什么。

脚本被人手动执行、被定时任务触发、被 Webhook 调用、被 AI Agent 使用以后，如果没有统一记录，排查问题只能靠猜。

谁触发的？传了什么参数？输出是什么？失败在哪一步？AI 调用过哪些工具？如果这些问题只能去日志文件、聊天记录和 CI 输出里拼，自动化越多，排障越慢。

ActionDock 会保存执行输入、输出、状态、日志和错误详情。外部事件进入平台后，也会保存事件记录、标准化结果和触发器派发结果。

平台还提供这些能力：

* CLI、CI 或外部系统可以用 Bearer Token 调用平台。
* 配置和 Secret 可以集中管理。
* 跨脚本共享状态可以设置过期时间和敏感值标记。
* 管理台可以导出和恢复系统数据包，用于升级前备份、环境迁移和故障恢复。

这些能力不会让脚本本身更复杂，但会让脚本进入长期运行环境后更稳。自动化不只要能跑，还要能回看、能解释、能追责。

---

## 工具多了以后，发现和更新才是问题

工具变多后，麻烦的不是"有没有"，而是"别人怎么发现、怎么安装、怎么更新、怎么知道自己装的是不是同一版"。

ActionDock 的 Repository 机制用来解决这个问题。

仓库里可以放脚本工具、插件、事件源资产、AI 能力包和 Skills。仓库可以来自 Git、HTTP 或本地目录。同步后，用户可以从管理台或 CLI 发现、安装和更新这些资产。

仓库资产不只包含源码，还可以带上依赖、调度模板和配置模板。安装时可以选择是否连同依赖一起安装，避免"脚本装好了，环境还缺一堆东西"。

仓库也支持工作副本与上游同步。仓库里的工具和事件源资产可以创建为本地工作副本，平台会通过上游绑定记录来源、版本、路径、提交和摘要，并判断当前状态是已同步、本地有改动、远端有改动，还是两边同时改动。

这样团队可以在平台里直接编辑和调试本地工作副本，同时保留与仓库上游的同步关系和更新通道。

## 内置 Skill：让 AI 直接调用你的脚本

让 AI 写一段代码并不新鲜。

真正麻烦的是：你已经有了一堆脚本，怎么让 AI 正确调用它们？

传统做法通常要自己写 Skill 或 Prompt。你要告诉模型有哪些脚本、每个脚本叫什么、参数怎么传、哪些字段必填、返回结果怎么看、什么时候可以调用。脚本本身维护一套逻辑，Skill 或 Prompt 里再维护一套说明。脚本参数一改，说明没同步，AI 就可能继续按旧方式调用。

ActionDock 想把这层适配内置掉。

平台提供一个面向 ActionDock 的内置 Skill。AI 客户端加载这个 Skill 后，就能理解 ActionDock 的脚本资产模型：什么是 `ScriptDefinition`，`inputSchema` 和 `outputSchema` 怎么描述参数，已发布脚本怎么作为稳定工具调用，执行结果、日志和错误在哪里查看。

也就是说，你不需要为了每个脚本再手写一份 AI 调用说明。

脚本发布以后，内置 Skill 可以让大模型直接调用它。模型不用靠 Prompt 猜参数，也不用你把脚本接口重新描述一遍；它可以基于脚本自己的 Schema 组织入参，通过 ActionDock 的统一入口执行脚本，并把结果返回到当前任务上下文里。

这和普通"把脚本贴给 AI"完全不同。

普通方式里，AI 拿到的只是一段代码片段，能不能跑、怎么传参、怎么复用，都要靠人继续补。ActionDock 里，AI 面对的是已经资产化的脚本：有 ID、有 Schema、有发布版本、有执行记录、有日志，也有统一调用入口。

更进一步，如果脚本还不存在，内置 Skill 还可以反过来帮你生成它。

你可以直接说：

"帮我写一个脚本，输入服务名和环境，检查健康接口。如果失败，返回失败原因；如果成功，返回状态、耗时和检查时间。"

大模型会按 ActionDock 的规范生成脚本草稿，包括源码、`inputSchema`、`outputSchema`、示例入参和使用说明。你可以在管理台里校验、试跑、调整，然后发布成稳定版本。发布之后，它又能被内置 Skill 直接调用。

这才是 ActionDock 里 Skill 的价值：不是让你多写一层提示词，而是把"生成脚本、发布脚本、调用脚本"串进同一套体系。

AI 负责把需求变成脚本，也负责在需要时调用脚本；ActionDock 负责让脚本可校验、可执行、可发布、可复用、可审计。

## 内置 AI 能力：脚本可以直接使用大模型

除了通过内置 Skill 让外部 AI 客户端理解和调用脚本，ActionDock 自己也内置了 AI 模型和 Agent 能力。

这带来的变化很大：脚本不再只能执行固定逻辑，也可以直接使用大模型。

过去，如果脚本里想用 AI，通常要自己接模型 API、管理 Key、拼请求、处理返回、记录用量和错误。每个脚本都接一遍，安全、审计和维护都会变散。

ActionDock 把模型配置收进平台。脚本可以通过内置 AI 能力调用聊天、结构化输出、向量或 Agent，而不是在脚本里硬编码模型地址和密钥。这样，脚本可以在流程中做判断、总结、分类、提取、生成内容，也可以把复杂任务交给 Agent 继续处理。

比如，一个告警处理脚本可以先拉取监控数据，再调用大模型总结异常原因；一个工单脚本可以读取用户描述，让模型提取字段和判断优先级；一个报表脚本可以生成结构化数据后，再让模型写出面向业务人员的摘要。

这解决的是另一类问题：不只是让外部大模型知道脚本怎么用，也不只是让 Agent 调脚本，而是让脚本、模型和 Agent 在同一个平台里互相配合，并把每一步调用都纳入平台治理。

在 ActionDock 中，Agent Profile 由几类内容组成：

* Model Profile：使用哪个模型、哪个供应商、什么 API Key。
* Toolset / Direct Tools：Agent 能调用哪些工具。
* Skills：Agent 具备哪些任务知识、流程约束和使用说明。

这样，一个 Agent 不只是 Prompt 里的几句话，而是一组可以被平台管理的运行配置：模型来自哪里、能调用哪些工具、权限边界是什么、执行过程如何记录，都有明确位置。

已发布的 `TOOL` 类型脚本会暴露为 ActionDock AI 工具，工具名是 `script.<scriptId>`。脚本的 `inputSchema` 直接变成工具输入结构，Agent 不需要靠 Prompt 猜参数。

Skill 在这里是 Agent 的知识层。它不是执行入口，更像是任务说明书：告诉 Agent 某类任务的背景、流程、边界和工具使用方式。真正执行动作的，是被加入 Toolset 的脚本工具。

比如做一个告警分诊 Agent：

* `send-message`、`query-oncall`、`create-ticket` 这些脚本发布后，加入 `incident-tools` Toolset。
* `incident-triage` Skill 说明告警如何判断等级、什么时候升级、信息怎么整理。
* Agent Profile 绑定模型、Toolset 和 Skill。

处理告警时，模型负责推理，Skill 管判断和流程，工具脚本管实际操作。每一次工具调用都会进入 ActionDock 的执行记录。

所以这里的重点不是让 AI 自由执行脚本，而是把模型、Agent、Skill、Toolset、脚本和审计放在同一个平台里。AI 可以参与自动化，但必须在已经定义好的工具、权限和记录边界内工作。

## 与拖拽式工作流工具的区别

n8n、Dify、扣子这类拖拽式工具很适合快速把几个现成节点串起来，也适合非技术人员配置简单流程。上手快，适合验证想法。

但很多自动化流程一开始很简单，后面会慢慢变复杂：条件分支越来越多，异常处理越来越细，依赖要复用，配置要区分环境，还要考虑版本、审计和代码评审。

继续在画布里堆节点，维护成本会逐渐上来。

ActionDock 的定位不同。它面向的是开发、运维、平台这类更习惯用代码表达逻辑的人，所以它的基础不是画布，而是脚本、Schema、插件和发布快照。

拖拽式平台复用的是节点；ActionDock 复用的是脚本和插件。

脚本适合沉淀流程步骤、业务动作和编排逻辑。插件适合沉淀内部 SDK、系统接入和稳定底层能力。

| 场景          | 拖拽式工作流       | ActionDock       |
| ----------- | ------------ | ---------------- |
| 主要使用者       | 非技术人员、业务配置人员 | 开发、运维、平台人员       |
| 基础表达方式      | 画布和节点        | 脚本、Schema、插件     |
| 复用单元        | 节点           | 脚本和插件            |
| 复杂逻辑        | 画布容易变重       | 用代码表达            |
| 版本、审计、分发    | 依赖平台能力       | 围绕脚本资产内建         |
| AI Agent 调用 | 通常需要再整理工具描述  | 直接基于 Schema 暴露工具 |

ActionDock 不是要替代所有可视化编排工具，而是把那些最终会变成脚本、服务或内部工具的流程，放进一套更贴近开发者工作方式的工程体系里。

## 快速开始

安装并启动：

```bash
npm install -g actiondock
actiondock server
```

启动后访问：

```text
http://localhost:5177/admin/app/scripts
```

运行一个内置示例：

```bash
actiondock script run hello-groovy --name alice --json
```

成功后会看到类似结果：

```json
{
  "status": "SUCCESS",
  "output": {
    "message": "Hello, alice!",
    "upperName": "ALICE"
  }
}
```

接下来可以继续尝试：

* 创建一个常用脚本，补充输入输出 Schema。
* 分别用 CLI 和管理台执行它。
* 发布脚本，生成稳定快照。
* 为脚本添加定时任务。
* 配置不同环境的 CLI profile。
* 把脚本发布到仓库，供其他人发现、安装和更新。
* 让内置 Skill 帮 AI 直接调用已发布脚本，或者先生成一份脚本草稿。
* 在脚本里直接调用平台内置 AI 能力，让自动化具备总结、判断、分类和生成能力。

## 总结

ActionDock 要解决的不是"怎么写脚本"，而是"怎么让脚本长期可用、可复用、可治理"。

它把脚本整理成有身份、有 Schema、有版本、有依赖、有配置、有执行记录的工具资产，并让这些资产可以被 CLI、管理台、REST API、定时任务、Webhook、其他脚本、内置 Skill 和 AI Agent 稳定调用。

对个人来说，它可以先是一个统一的脚本管理和自动化入口。

对团队来说，它可以承接脚本分发、环境隔离、执行审计、插件复用、仓库管理和 AI 工具化。

更重要的是，它让脚本和 AI 之间不再只靠 Prompt 临时拼接：AI 可以通过内置 Skill 理解并调用脚本，脚本也可以直接使用平台内置的大模型能力。

脚本不缺。真正缺的是让脚本长期可靠运行的工程体系。

ActionDock 想补上的，就是这一层。
