# ActionDock 演讲备注

> 配套 [actiondock-presentation.md](./actiondock-presentation.md) 使用。本文档不是逐字稿，而是每页的讲述重点、过渡句和控时建议，适合 20-30 分钟内部分享。

---

## 整体讲法

### 这场分享的主线

不要把它讲成“大平台介绍”，而是讲成一条很具体的线：

1. 我们今天本地脚本到底哪里不顺
2. 为什么 Skill 和文档之外，仍然需要执行能力底座
3. ActionDock 用很小的介入成本把脚本统一成稳定工具
4. 完整 CLI 让大模型可以把脚本开发流程真正跑起来
5. 团队应该先从哪类脚本开始接

### 控时建议

- 前 1-6 页：8 分钟
- 7-12 页：8 分钟
- 13-22 页：8 分钟
- 23-25 页：3-5 分钟

### 讲述原则

- 先讲问题，再讲能力
- 先讲低门槛，再讲完整能力
- 架构页只讲结论，不展开实现细节
- 所有能力页都回扣一句：`它解决的是本地工具复用问题`

### 不要这样说

- 不要说 `Skill 不能复用`
- 不要说 `ActionDock 替代 Skill`
- 不要把 Skill 和脚本讲成同一层能力
- 不要说 `产品内置了全自动 AI 写脚本`

### 应该这样说

- Skill 复用的是知识、步骤和上下文
- ActionDock 复用的是可执行能力、契约和运行时
- 两者结合时，AI 才既知道怎么做，也真的有工具可调
- 在合适约束下，模型可以通过 Skill + CLI 走完整个脚本开发闭环

---

## 封面

### 要讲什么

- 今天不讲一个“要上线的大平台”
- 今天讲的是怎么把大家本地已经在用的脚本，变成更容易复用和共享的工具

### 可以直接说

“这次分享我想讲的不是怎么再造一套平台，而是怎么把我们手里已经存在的大量本地脚本，变成真正能复用、能分享、能被 AI 调用的工具资产。”

### 过渡

“先不说框架，先看我们今天管理本地脚本的方式到底有什么问题。”

---

## 痛点 — 我们今天怎么管理本地脚本？

### 要讲什么

- 这页不要讲抽象概念，要讲大家都遇到过的场景
- 强调问题不是“没有脚本”，而是“很多复用停留在知识层，能力层没有沉淀”

### 可以直接说

“我们其实不缺脚本，也不缺各种 README、命令片段，甚至 Skill。问题在于，这些东西很多只能共享‘怎么做’，不一定能共享‘一个稳定可执行的能力’。”

“一旦这个脚本想给第二个人用，成本就上来了。你得解释参数、解释环境、解释执行方式。别人拿到以后，往往还要自己再包一层，或者再写一层 Skill 去描述它。”

### 这页要压住的重点

- 不要讲上线事故
- 不要讲企业治理
- 就讲本地使用下的交接、复用和共享成本

### 过渡

“如果只是一次性脚本，这些问题可以忍。但只要开始重复使用，它就会从个人脚本变成一个能力沉淀问题。”

---

## 为什么本地工具也会失控

### 要讲什么

- 这一页要完成一个认知转折：本地脚本不是天然轻量，而且知识复用不等于能力复用

### 可以直接说

“脚本第一次写出来的时候，它只是个人效率工具。第二次还能忍。第三个人开始用的时候，问题就不再是代码能不能执行，而是它有没有稳定接口、有没有统一入口、别人能不能发现。”

“这里要特别区分一下：Skill、Prompt、文档当然也是复用，但它们复用的是知识和步骤。我们现在缺的是执行层的复用。”

### 这一页的目标

- 让听众认同：有些本地脚本确实值得被管理

### 过渡

“那 ActionDock 想做的，其实不是替代 Skill，也不是替代大家写脚本，而是给这些已经值得复用的脚本补一个统一执行外壳。”

---

## ActionDock 是什么

### 要讲什么

- 给出一句话定义
- 重点落在“本地自动化工作台”

### 可以直接说

“ActionDock 可以把它理解成一个可扩展的本地自动化工作台。核心不是换语言，而是让同一份脚本定义可以被不同入口复用。”

“你写一次脚本，后面可以从 UI、CLI、API、Agent、定时任务、Webhook 去触发它，不用每个入口都再包一遍。”

### 过渡

“这里很重要的一点是，它并不打算改变你写脚本这件事本身。它也不是去跟 Skill 抢位置。”

---

## Skill、脚本、ActionDock 分别解决什么

### 要讲什么

- 这是整场里最重要的去混淆页
- 明确三者不是竞争关系，而是上下层关系

### 可以直接说

“我这里想专门拆一下 Skill、脚本和 ActionDock。Skill 更像知识包，负责告诉 AI 或使用者在什么场景按什么步骤做什么。脚本是真正完成动作的能力单元。ActionDock 则是把这些脚本包装成稳定工具的执行底座。”

“所以如果把 Skill 看成‘告诉 AI 怎么做’，那 ActionDock 就是‘把能做的事沉淀成稳定工具’。”

### 这页一定要讲清楚的结论

- Skill 在上层，负责上下文和操作约定
- Script 在中间，负责具体动作
- ActionDock 在下层，负责把 Script 做成稳定可调用能力

### 过渡

“理解了这个分层，后面就不会再把它看成一个重型替代方案。”

---

## Skill + CLI：让大模型不只会说，还能直接做

### 要讲什么

- 这是新增的强亮点页
- 强调 CLI 是完整自动化接口，不只是命令行入口

### 可以直接说

“这里我想补一个很重要的亮点。ActionDock 不只是把脚本变成工具，它还有完整的 CLI 模块。也就是说，大模型如果拿到了正确的 Skill 约定，它不是只能给你一段代码，而是可以继续把创建、修改、校验、发布、执行这些步骤真的跑完。”

“换句话说，Skill 让模型知道该怎么操作，CLI 让模型真的有东西可以操作。”

### 这页要落到的事实

- CLI 已覆盖 `create / patch / validate / publish / run`
- 脚本页可以生成 `Skill 示例`
- Skill 示例还能进一步发布为 Skill 包

### 表述边界

- 讲成 `在合适约束下可做到端到端`
- 不要讲成 `完全不需要人看`

### 过渡

“所以后面再看这个框架的时候，不要只把 CLI 理解成一个方便人工操作的入口，它其实也是模型自动化开发流程的接口面。”

---

## 它不替代你写脚本，它只是给脚本一个统一外壳

### 要讲什么

- 降低心理门槛
- 明确这不是重型替换方案

### 可以直接说

“这套东西不是要你把脚本改造成微服务，也不是要求一开始就部署成团队公共平台。你原来怎么写 Groovy、怎么写 Python，基本可以保持不变。”

“它主要补的是外层定义：参数是什么、输出是什么、运行时有哪些统一能力、别人该怎么调用。这样 Skill 或 Agent 调用到的，不再只是说明，而是稳定工具。”

### 这页要强调的结论

- 成本主要是补 Schema 和描述
- 不是重写业务逻辑

### 过渡

“如果把它和我们现在常见的几种方式放在一起看，它的位置会更清楚。”

---

## 产品定位对比

### 要讲什么

- 这页不要逐行念表
- 只抓 3 个最关键差异

### 建议讲法

重点讲三点：

1. `inputSchema/outputSchema` 让脚本第一次有了稳定契约
2. 多入口共用一份定义，避免重复包壳
3. 仓库让本地工具开始具备团队共享能力

### 可以直接说

“如果只是脚本目录，它解决的是‘我自己能跑’。如果临时封成 API，它解决的是‘系统能调’。而 Skill 更多解决的是‘AI 知道怎么用’。ActionDock 补的是中间缺掉的那层：把能力本身做成稳定工具。”

“再往前一步，因为它有完整 CLI，所以这个稳定工具不仅能被人使用，也能被模型驱动整个开发和发布过程。”

### 过渡

“那它是怎么做到这件事的？核心不是代码本身，而是把脚本定义成一个完整资产。”

---

## 核心概念 — 脚本资产

### 要讲什么

- 解释“资产化”到底增加了什么

### 可以直接说

“所谓脚本资产化，不是把代码神秘化，而是给它补齐元信息。除了源码本身，还要有 ID、描述、输入输出 Schema、依赖声明。这样脚本才不是一段只能自己看的代码，而是一个别人或者 Skill/Agent 都能直接调用的工具。”

“这里最关键的是 Schema，因为它会同时驱动 UI 表单、CLI 参数和 AI 工具描述。”

### 过渡

“有了这个定义之后，脚本就不只是能写、能跑，还会有一个稳定版本概念。”

---

## 脚本生命周期

### 要讲什么

- 重新定义“发布”
- 避免听众误解成上线发布

### 可以直接说

“这里的发布不要理解成上线，它更像是你把当前版本冻结成一个稳定快照。草稿版继续改，但给别人复用、给 Agent 调用、给定时任务执行的，是那个你确认过的稳定版本。”

“这样你就把‘我正在改的版本’和‘别人正在用的版本’分开了。”

### 这一页的价值

- 让听众明白平台不是在增加流程，而是在降低混乱

### 过渡

“一旦有了稳定定义和稳定版本，同一份脚本就可以自然支持多个入口。”

---

## 多入口执行 — 同一脚本，多种调用方式

### 要讲什么

- 这页讲“统一入口收益”
- 不要逐个接口细讲

### 可以直接说

“这页最重要的不是记住有哪些入口，而是理解这些入口用的是同一份定义。以前是每多一个入口，就多包一层。现在是脚本一旦定义好了，UI、CLI、API、Agent 都可以直接复用。”

“这也是为什么它适合本地自动化。你可以先自己在 CLI 跑，后面再给别人通过 UI 跑，再后面再开放给 Agent 调。”

### 过渡

“如果现场演示，我建议只证明这一点就够了，不要试图演完整个平台。尤其可以顺手带出 CLI 闭环，让大家看到它不只是 run 一下脚本。”

---

## Demo 应该证明什么

### 要讲什么

- 管住 Demo 范围
- 让 Demo 服务主线

### 可以直接说

“Demo 我建议只演一个最小闭环。拿一个真实本地脚本，补一个 Schema，在 UI 跑一次，在 CLI 跑一次，发布成稳定版本，再演示它被其他脚本、Agent 或 Skill 场景消费。这样听众会很清楚地看到：原来只是本地代码，现在已经变成了一个可复用工具。”

“如果想把‘模型自动开发脚本’这个亮点讲出来，可以再补一句：同样这套流程，如果模型拿到了 Skill 约定，也可以通过 CLI 把 create、validate、publish、run 这几步走完。”

### 不建议现场演的内容

- 不要同时演仓库、事件、插件、AI 全链路
- 不要把 Demo 变成功能巡礼

### 过渡

“那接下来一个很实际的问题就是：我们到底应该先把什么样的脚本接进来？”

---

## 什么脚本最适合先接入

### 要讲什么

- 给团队一个明确的切入标准

### 可以直接说

“不是所有脚本都值得接入。最适合的，通常是那些你们已经在反复运行、已经开始发给别人、或者已经想从多个入口调用的脚本。”

“反过来，一次性实验脚本没必要强行资产化。否则团队会觉得平台在增加负担。”

### 过渡

“所以比较好的 adoption 方式，不是全面迁移，而是从个人效率最明确的地方开始。”

---

## 个人效率到团队共享的 adoption 路径

### 要讲什么

- 这一页是 adoption 核心
- 讲顺序，不讲大而全

### 可以直接说

“我更推荐的接入顺序是，先解决个人复用，再解决团队共享，然后再慢慢接自动化入口和 AI。不要一开始就把仓库、事件、插件、AI 全打开。那样成本感会非常强。”

“这个框架最大的好处，是可以从一个人电脑上的一个高频脚本开始起步。”

### 过渡

“如果大家想知道它内部为什么能支撑这些入口，后面几页我会快速带一下实现结构，但重点还是看它给脚本带来了什么能力。”

---

## 脚本执行架构

### 要讲什么

- 讲结论，不深挖内部类名

### 可以直接说

“这页可以简单理解成：上层入口很多，但中间都汇聚到一个统一的脚本调用服务，再由底层脚本引擎去执行 Groovy 或 Python。脚本运行时能拿到统一上下文，所以它们之间可以互相调用，也可以访问插件、状态和配置。”

### 控时

- 30 到 45 秒足够

### 过渡

“比起内部结构，大家实际更关心的是：脚本拿到这个运行时以后，具体能做什么。”

---

## 脚本运行时 API

### 要讲什么

- 这一页讲“脚本不是孤立的”

### 可以直接说

“脚本进入 ActionDock 以后，价值不只是能被运行，而是它拿到了统一运行时。它可以调用别的脚本，可以调用插件，可以调用 AI，也可以读写共享状态。”

“换句话说，本地脚本从一个单点文件，变成了一个可以组合的工具节点。”

### 过渡

“如果团队里开始出现越来越多这种工具节点，下一步自然就是：怎么把它们分享给别人。”

---

## 仓库与分发

### 要讲什么

- 把仓库讲成工具分发，不要讲成部署系统

### 可以直接说

“这部分我建议直接把它理解成工具包管理器。个人写的常用脚本，后面可以发布到仓库，让团队成员去发现、安装、更新，而不是继续靠发文件或者扔 Git 地址。”

“这一步很关键，因为它意味着脚本开始从个人效率工具，变成团队公共资产。”

### 过渡

“有些同学会问，那 AI 在这里是什么位置？我的建议是，把 AI 看成接入后的增益，而不是前置条件。”

---

## AI 原生集成

### 要讲什么

- 降低 AI 神秘感
- 讲清楚价值是“脚本可被 AI 调用”

### 可以直接说

“AI 这块最有价值的地方不是聊天接口本身，而是你已经定义好的脚本可以直接注册成工具，让 Agent 调用。这样 AI 不再绕过你的工具体系，而是复用已经沉淀好的脚本资产。”

“如果再叠加 Skill，那 Skill 负责补上下文和规则，ActionDock 负责提供真实工具。这样 AI 既知道怎么做，也真的有工具可做。”

### 过渡

“除了脚本本身，平台也允许把更重一点的能力封装成插件。”

---

## 插件系统

### 要讲什么

- 解释插件和脚本的分工

### 可以直接说

“脚本适合快写快改，插件适合那些依赖重、性能要求高、需要访问本地资源的能力。对脚本作者来说，两者体验是统一的，都是调用一个动作。”

“这意味着平台核心不用预置所有能力，但又能保持扩展一致性。”

### 过渡

“如果除了人和 AI，我们还想让外部事件触发这些工具，就会用到下面这层。”

---

## 事件驱动框架

### 要讲什么

- 把它当成进阶能力带过

### 可以直接说

“事件这块我建议作为进阶能力理解。它的意义是，本地工具不一定只能手动运行，也可以被外部系统标准化触发。比如某个 Webhook 过来以后，经过过滤和参数映射，直接调用脚本。”

### 控时

- 30 秒左右，不展开处理器细节

### 过渡

“到这里可以看到，这个框架不是单纯在管理脚本文件，而是在补整套工具沉淀所需的运行上下文。”

---

## 治理能力

### 要讲什么

- 把治理讲成共享能力，而不是企业合规

### 可以直接说

“这里的治理不要理解成很重的管理动作，它更像是本地工具要长期复用时必须补上的公共能力。比如配置集中管理，状态集中存放，敏感信息自动脱敏，必要时可以留访问令牌和备份恢复。”

“这些东西的价值在于，脚本开始不再依赖作者自己的本地习惯。”

### 过渡

“如果把这些能力都落到一个操作面上，管理台和 CLI 就是两个最直接的入口。”

---

## 管理台 UI

### 要讲什么

- 告诉听众 UI 是为了降低非作者使用门槛

### 可以直接说

“管理台的意义，不是把命令行替掉，而是让非作者也能更容易发现、运行和管理这些工具。尤其当脚本开始被多人共享时，UI 会明显降低使用门槛。”

### 过渡

“如果你更偏命令行工作流，那 CLI 会更有感觉。”

---

## CLI 工具

### 要讲什么

- 强调 CLI 是本地自动化的自然入口，也是模型自动化的接口面

### 可以直接说

“CLI 其实很符合这套框架的气质，因为很多本地脚本本来就是从命令行起步的。Schema 自动展开成 flag 以后，脚本就不再只是一个源文件，而是一个可调用命令。”

“更重要的是，这个 CLI 不是只有一个 run 命令，而是覆盖了 create、patch、validate、publish、run 整个生命周期。所以它不只是方便人用，也天然适合被大模型或 Skill 驱动。”

### 这页要特别点出的命令

- `actiondock script create`
- `actiondock script patch`
- `actiondock script validate`
- `actiondock script publish`
- `actiondock script run`

### 过渡

“前面更多是能力视角，最后给大家补一页技术可信度。”

---

## 技术亮点

### 要讲什么

- 这一页是建立技术信任，不是展开细节

### 建议讲法

只挑 2-3 点说：

- 脚本和外部依赖解耦
- Python 不是硬嵌，而是桥接执行
- 已发布 TOOL 自动注册为 AI 工具

### 可以直接说

“这页更多是给大家一个技术上的信心：这套东西不是把很多能力硬糊在一起，而是有比较清晰的分层和扩展方式。”

### 过渡

“但我最后还是想把边界讲清楚，避免把它理解成万能方案。”

---

## 适用边界

### 要讲什么

- 主动讲限制，增加可信度

### 可以直接说

“这套东西不是零成本的。你需要给脚本补 Schema、补描述，也需要决定哪些脚本值得沉淀。一次性实验代码没必要进来，否则团队只会觉得负担变重。”

“它最适合的是那些已经有复用趋势的本地工具，而不是所有代码。”

### 过渡

“如果接受这个边界，它带来的价值就会非常明确。”

## 总结

### 要讲什么

- 回扣整场主线

### 可以直接说

“如果用一句话总结，ActionDock 解决的不是‘怎么写脚本’，而是‘怎么让本地脚本真正变成团队可复用的执行能力’。”

“它最有价值的地方不是功能多，而是让一份本地脚本开始具备稳定契约、多入口复用、可共享安装、可被 AI 调用这些能力。”

“如果把 Skill 看成‘告诉 AI 怎么做’，那 ActionDock 就是‘把能做的事沉淀成稳定工具’。”

“再进一步，因为它有完整 CLI，所以在合适约束下，大模型甚至可以把这个稳定工具从创建到发布整条链路都走完。”

### 收尾句

“如果团队里已经有一批常用本地脚本，我认为这套东西是非常值得介入的。”
