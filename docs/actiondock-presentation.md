## 痛点 — 我们今天怎么管理本地脚本？

**你一定遇到过这些情况：**

- 接手别人的脚本，光是搞清楚怎么跑就要问半天
- README 写得很详细，但每次执行还是要翻文档
- 把脚本分享给同事，要么丢文件、要么发 Git 链接，执行起来还是各自折腾
- 想让 AI 帮忙调用脚本，结果就是 prompt 拼接 prompt，效果不稳定
- 团队里每个人都有自己的小工具，但没人知道别人的工具存在

**说白了：知识能共享，但能力很难复用。**

---

## 为什么本地工具总是"管不住"

### 复用容易停留在"知道怎么做"，而不是"真的能跑"

一个脚本的生命周期往往是这样的：

- **第一次写**：满足自己当前的需求，跑通了就行
- **第二次用**：发现之前写得糙，改一改继续跑
- **第三个人接手**：开始疯狂问问题——参数怎么填？依赖装了吗？这步什么意思？

到这一步，问题就来了：**知识的传递是免费的，但能力的传递需要契约。**

### 什么时候该"治理"你的脚本

满足以下任一条件，这个脚本就值得认真对待了：

- 不只是自己在用
- 不只跑一次
- 需要从不同地方触发（CLI、UI、AI、定时任务……）
- 想让 AI 来调用它
- 需要保留执行记录或共享状态

### 两种"复用"的区别

| 类型 | 你得到的是 |
|------|-----------|
| Skill / Prompt / 文档 | 知道步骤和思路，但还是要自己执行 |
| ActionDock | 一个可以直接调用的工具，参数、输入输出都是明确的 |

## ActionDock 是什么

### 一句话

> ActionDock 是一个把脚本变成可定义、可运行、可分发、可被 AI 调用的工具底座。

### 它做了什么：给脚本穿上一套"标准外套"

一份脚本定义好之后，可以从这些地方直接调用：

- **管理台** — 点鼠标运行
- **CLI** — 写进自动化流程
- **REST API** — 集成到其他系统
- **AI Agent** — 让大模型帮你调用
- **定时任务** — 定期自动跑
- **Webhook** — 被外部事件触发

你只需要定义一次脚本的能力（输入什么、输出什么），之后的事交给 ActionDock。

## Skill、脚本、ActionDock 各干各的活

### 三者有关系，但不在同一层

| | 解决的问题 | 打比方 |
|------|-----------|---------|
| **Skill** | 告诉 AI”什么时候调用、怎么调用” | 给你一张任务卡 |
| **脚本** | 真正完成具体动作 | 实际干活的人 |
| **ActionDock** | 让脚本变成稳定的可调用工具 | 给干活的人配工牌和工位 |

### 配合起来是什么样

```
Skill 说：”用户要生成日报了，去调那个工具”
           │
           ▼
ActionDock 执行：generate-report(inputSchema, outputSchema, state, log...)
```

没有 ActionDock，Skill 只能给你一段说明——“先这样，再那样”。
有了 ActionDock，Skill 可以直接说”调用 generate-report”，然后真的拿到结果。

## 它不替代你写脚本，只是给脚本加个"工牌"

### 用 ActionDock 不需要你改变什么

- 不用把脚本改成微服务
- 不用一开始就跑团队级部署
- 不用非得接 AI
- 用 Groovy、Python 随便你

### ActionDock 实际上做了什么

- **补 Schema** — 告诉别人"这个脚本要什么输入、会吐出什么输出"
- **给运行时** — 提供 `plugins`、`scripts`、`state`、`config` 这些能力
- **提供多入口** — UI、CLI、API、AI 都可以调用同一份脚本
- **支持分发** — 发布到仓库，团队成员可以安装、更新
- **让 Skill 有东西可调** — 不只是拿到说明，而是真的能调用并拿到结果

### 最小介入路径

```
现有脚本
   │
   ├── 补一个 inputSchema / outputSchema（可能就几十行）
   ├── 放进 ActionDock
   └── 搞定——立即获得多入口调用能力
```

## 和其他方案对比

| | 本地脚本目录 | 临时封装 API | ActionDock |
|------|-------------|---------------|------------|
| **输入输出约定** | 靠注释或口头 | 手写 DTO | Schema 一次声明，处处生效 |
| **调用入口** | 命令行为主 | API 为主 | UI / CLI / API / AI 全都支持 |
| **分享方式** | 发文件 / 发链接 | 重新部署 | 仓库安装，一键更新 |
| **接 AI** | prompt 拼接 | 额外封装 | 原生支持，脚本自动注册为工具 |
| **共享状态** | 各写各的 / 自建 Redis | 另接状态服务 | 内置 namespace + CAS |
| **扩展能力** | 各写各的 SDK | 改服务代码 | PF4J 插件统一扩展 |
| **适合场景** | 个人能跑 | 系统对接 | 本地工具资产化 + 团队共享 |

## 核心概念 — 脚本资产

### 一个脚本不只是代码，是一个"工具"

```
Script Definition
├── Script ID        ← 唯一标识
├── 名称 / 描述
├── 类型             ← Groovy | Python
├── 打包类型         ← TOOL（单次调用）| FLOW（多步骤）
├── inputSchema      ← 告诉别人要填什么参数
├── outputSchema     ← 告诉别人会拿到什么结果
├── 依赖声明         ← 需要哪些插件或脚本
└── 源码             ← 实际执行的代码
```

### Schema 声明一次，这些地方自动用上

| 调用方 | Schema 怎么用 |
|--------|-------------|
| CLI | 自动变成 `--name alice` 这样的命令行参数 |
| 管理台 | 自动生成填写表单 |
| AI Agent | 自动理解成 tool description |
| 执行引擎 | 执行前自动校验参数格式 |

## 脚本生命周期

### “发布”在这里的意思是”冻结一个稳定版本”

```
     创建
       │
       ▼
    ┌──────┐
    │ 草稿  │ ←── 在修改、调试、试跑
    │ DRAFT │     可以用 --draft 执行草稿版
    └──┬───┘
       │ 发布（冻结当前状态）
       ▼
  ┌───────────┐
  │  已发布   │ ←── 供别人使用、给 Agent 调用、
  │PUBLISHED  │     给定时任务执行
  └──┬────┬──┘
     │    │
     │    └── 归档（不用了但留档）
     │
     └── 丢弃草稿 → 回到上一个稳定版本
```

| 来源 | 你能做什么 |

| Fork 副本 | 完全控制 |
| 开发仓库同步 | 双向同步 |
| 系统示例 | 只读 |

## 多入口执行 — 同一个脚本，怎么调用都行

### 管理台
打开脚本库 → 点脚本 → 填参数 → 看结果

### CLI
```bash
actiondock script run hello-groovy --name alice --json
```

### REST API
```bash
curl -X POST http://localhost:5177/api/scripts/hello-groovy/execute \
  -H 'Content-Type: application/json' \
  -d '{"input": {"name": "alice"}, "mode": "SYNC"}'
```

### 定时任务
触发中心 → 定时触发 → 选脚本 → 设 Cron → 自动跑

### Webhook
外部系统发请求 → 标准化处理 → 过滤匹配 → 执行脚本

### AI Agent
Agent 分析任务 → 决定调用哪个工具 → 执行脚本 → 返回结果

## 什么脚本值得先接入

### 优先接入这几类

1. **经常手动跑的** — 你或同事总是重复执行某个脚本
2. **参数记不住的** — 每次都要翻 README 或源码
3. **想多入口调用的** — 同时想从 CLI、UI、AI 跑
4. **已经发给别人的** — 开始有团队共享需求
5. **想暴露给 AI 的** — 希望 Agent 能调用

### 别急着接入的

- 临时实验脚本
- 输入输出还没定型的探索代码
- 强依赖本地交互环境的

## 脚本执行架构

```
调用入口                    服务层                  引擎层
┌────────┐                ┌───────────┐          ┌──────────────┐
│REST API│──┐             │           │          │ ScriptEngine  │
├────────┤  │             │  Script   │          │   接口        │
│  CLI   │──┼────────────→│Invocation │─────────→│              │
├────────┤  │             │  Service  │          ├──────────────┤
│UI 手动 │──┤             │           │          │ GroovyEngine │
├────────┤  │             │           │          │ (JVM 内编译)  │
│Agent   │──┘             └───────────┘          ├──────────────┤
└────────┘                                       │ PythonEngine │
                                                 │ (子进程执行)  │
                                                 └──────────────┘
                                                        │
                                                 ┌──────┴──────┐
                                                 │ 上下文注入    │
                                                 │ plugins      │
                                                 │ scripts      │
                                                 │ state        │
                                                 │ config       │
                                                 │ log          │
                                                 └─────────────┘
```

**技术细节：**
- Groovy 在 JVM 内编译执行，编译结果会缓存
- Python 通过子进程执行，用 stdin/stderr 通信
- 两种语言可以互相调用——Groovy 调 Python、Python 调 Groovy 都可以

## 脚本运行时 API

### 调用其他脚本（跨语言透明）

```groovy
// Groovy 里调 Python 脚本
def result = scripts.invoke("target-script", [param1: "value1"])
```

```python
# Python 里调 Groovy 脚本
result = scripts.invoke("target-script", {"param1": "value1"})
```

### 调用插件

```groovy
// 统一调用接口
def result = plugins.invoke("my-plugin", "action-name", [key: "value"])
```

### 调用 AI

```groovy
// 在脚本里直接用 AI 能力
plugins.invoke("actiondock-ai", "chat", [
    modelProfileId: "my-model",
    messages: [[role: "user", content: "Hello"]]
])
```

### 共享状态（带并发保护）

```groovy
state.get("ns", "key")           // 读取
state.put("ns", "key", [data: "value"])  // 写入
state.cas("ns", "key", [data: "new"], 3) // CAS：只有版本号是 3 才写入成功
```

## 治理能力

### 配置值管理

- 存 API Key、连接字符串等
- **Secret 脱敏** — 敏感值在 UI 和日志里自动隐藏
- **引用追踪** — 知道哪些脚本和模型用了某个配置
- **模板引用** — 支持 `${config.key}` 占位符

### 共享状态

- `namespace + key` 组织，命名空间隔离
- `version` + CAS 乐观锁，并发安全
- `expiresAt` 自动过期
- 完整记录（谁写的、哪个执行触发的）

### 访问令牌

- 格式: `adk_{id}_{secret}`
- SHA-256 哈希存储
- **开放模式**: 没配置令牌时所有请求免认证
- 创建后只显示一次，记得保存

### 数据备份

- 14 种数据类型都能备份
- 支持 Secret 值排除/包含
- 恢复前先预览分析（会创建几个、覆盖几个、跳过几个）

## 进阶能力：让大模型帮你写脚本

### 这是高级玩法，不用第一天就用

前提：
- 人先把目标、边界、验收标准说清楚
- 模型负责补代码、补 Schema、跑 CLI
- 人负责确认结果，不是把高风险操作全交给 AI

### 怎么工作的

```
人描述目标
  └── 模型生成代码和 Schema
       └── 通过 CLI 执行 create / patch / validate / publish / run
            └── 人确认结果对不对
```

### 为什么能成立

- CLI 已经覆盖了脚本从创建到发布的全流程
- Schema 让模型能稳定地补输入输出约定
- Skill 可以给模型补充步骤和约束说明

---

## 技术亮点

### 1. 端口与适配器架构
核心领域层不依赖具体实现（Spring、JPA、AI Provider），外部依赖通过端口接口解耦。

### 2. Python 子进程桥接
Python 引擎通过 stdin/stderr 协议与 Java 主进程通信，支持脚本互调、插件调用、状态操作，无需嵌入 Python 解释器。

### 3. 脚本自动注册为 AI 工具
已发布的 TOOL 类型脚本自动进入 ToolRegistry，Agent 可以自主发现和调用。

### 4. 事件处理管道
标准化 → 过滤 → 幂等 → 输入映射，四阶段管道确保事件处理的可靠性。

### 5. CAS 乐观锁
共享状态带版本号，用 Compare-And-Swap 保证并发安全。

### 6. 开放模式 + 安全模式
没配置令牌时全开放（方便开发），配了令牌后自动启用认证。

---

## 适用边界

### 不是零成本，也不是万能

- 需要补 Schema 和描述，有一定治理成本
- 不是所有脚本都值得接入，一次性脚本别硬塞
- 团队共享需要基本的仓库和发布规范
- AI 工具调用从最小权限开始，别一上来就给高风险能力

### 更适合的场景

- 反复运行的本地工具
- 想让多人复用的脚本
- 想统一成多入口的能力
- 想长期沉淀为团队工具库的逻辑
