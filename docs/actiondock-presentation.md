## 痛点 — 我们今天怎么管理本地脚本？

```
┌─────────────────────────────────────────────────┐
│  每个人电脑一堆脚本    │  只有作者自己知道怎么跑   │
│  README / Skill / 注释 │  能共享知识，难共享执行力   │
│  复制文件 / 发 Git 链接 │  分享容易，稳定调用很难     │
│  prompt 拼接 AI        │  能跑，但缺统一执行底座     │
└─────────────────────────────────────────────────┘
```

### 我们日常真正遇到的问题

1. **脚本能执行，但不能交接** — 参数、依赖、环境约定都在脑子里
2. **知识能共享，能力难沉淀** — 文档、命令片段、Skill 可以传播，但稳定工具难复用
3. **入口越来越多** — CLI、UI、AI、Webhook 各接一套
4. **状态和日志分散** — 控制台、临时文件、本地目录各存一份
5. **团队工具沉淀不下来** — 每个人都在重复造相似的小工具

---

## 为什么本地工具也会失控

### 问题不在“没有复用”，而在“复用经常停留在知识层”

```
第一次写出来           第二次重复用           第三个人开始用
     │                      │                      │
     ▼                      ▼                      ▼
  个人脚本              常用工具雏形           团队共享成本开始上升
                                                  │
                                                  ▼
                                  需要稳定参数、统一入口、可执行能力底座
```

### 本地脚本一旦满足下面任意一条，就值得治理

- 被第二个人使用
- 被第二次重复执行
- 需要从不同入口触发
- 需要接 AI、定时任务或事件
- 需要保留共享状态或结果记录

### 这里要区分两种复用

- **Skill / Prompt / 文档** 复用的是知识、步骤和上下文
- **ActionDock** 复用的是可执行能力、参数契约和运行时

## ActionDock 是什么

### 一句话定义

> ActionDock 是一个可扩展的本地自动化工作台，也是把脚本沉淀为可执行工具的底座。

### 它统一的不是语言，而是脚本的外壳

```
同一份脚本定义
    │
    ├── 管理台（UI）─────── 人工运行
    ├── CLI ────────────── 本地自动化
    ├── REST API ───────── 本地集成
    ├── AI Agent ───────── 智能调用
    ├── 定时任务 ───────── 周期执行
    └── Webhook 事件 ───── 外部触发
```

**一次定义，多种入口复用。**

## Skill、脚本、ActionDock 分别解决什么

### 这三者有关，但不在同一层

| 层次 | 解决的问题 | 更像什么 |
|------|-----------|---------|
| Skill | 告诉 AI 或使用者“该做什么、按什么步骤做” | 知识包 / 操作约定 |
| Script | 真正执行某个动作 | 能力单元 |
| ActionDock | 把脚本变成可定义、可运行、可分发、可被 AI 调用的工具 | 执行底座 |

### 更直接的理解

- Skill 负责表达意图和上下文
- 脚本负责完成具体动作
- ActionDock 负责把脚本包装成稳定能力，让 UI、CLI、API、Agent、仓库都能复用

### 一个例子

```text
Skill：当用户要生成日报时，调用日报工具，并按指定格式回复
  │
  ▼
ActionDock Script：generate-report(inputSchema, outputSchema, state, log, plugins...)
```

没有 ActionDock，Skill 更像“说明怎么做”。
有了 ActionDock，Skill 才能稳定调用一个已经定义好的工具。

## 它不替代你写脚本，它只是给脚本一个统一外壳

### ActionDock 不做什么

- 不要求把脚本改造成微服务
- 不要求一开始就做团队级平台部署
- 不要求先接 AI 才能用
- 不限制你写 Groovy 还是 Python

### ActionDock 实际做的事

- 给脚本补上 `inputSchema` / `outputSchema`
- 给脚本提供统一运行时：`scripts` / `plugins` / `state` / `config`
- 把脚本变成 UI、CLI、API、Agent 都能调用的工具
- 让本地工具可以被发布、共享、安装、更新
- 让 Skill 或 Agent 有稳定能力可以调用，而不是只拿到说明文件

### 最低介入模型

```
现有脚本
   │
   ├── 补输入输出 Schema
   ├── 放进 ActionDock
   └── 立即获得 UI / CLI / AI / 调度入口，并可被 Skill/Agent 消费
```

## 产品定位对比

| 维度 | 本地脚本目录 | 临时封装成 API | ActionDock |
|------|-------------|---------------|------------|
| 输入输出契约 | 注释 / 口口相传 | 手写 DTO | 内建 `inputSchema` / `outputSchema` |
| 运行入口 | 命令行为主 | API 为主 | UI / CLI / API / Agent 共用 |
| 分享方式 | 发文件 / 发链接 | 重新部署 | 仓库发现、安装、更新、开发同步 |

| 共享状态 | 文件 / Redis 自管 | 另接状态服务 | 内建 `namespace + key + CAS` |
| 扩展能力 | 各写各的 SDK | 改服务 | PF4J 插件统一调用 |
| 复用层级 | 复用代码片段 | 复用接口 | 复用可执行能力与运行时 |
| 适用定位 | 个人可跑 | 系统对接 | 本地工具资产化与团队共享 |

## 核心概念 — 脚本资产

### 脚本不是一段源码，而是一个完整的工具定义

```
Script Definition
├── Script ID        ← 唯一标识
├── 名称 / 描述
├── 类型             ← GROOVY | PYTHON
├── 打包类型         ← TOOL（单次调用）| FLOW（多步骤）
├── inputSchema      ← JSON Schema，驱动表单/CLI/AI
├── outputSchema     ← 输出结构定义
├── 依赖声明         ← 脚本 / 插件 / AI
└── 源码             ← 实际代码
```

### Schema 一次声明，四处生效

| 消费方 | Schema 的作用 |
|--------|-------------|
| CLI | 自动展平为 `--name alice` 形式的 flag |
| Admin UI | 自动生成参数填写表单 |
| AI Agent | 自动理解为 tool description |
| 执行引擎 | 执行前自动校验入参格式 |

## 脚本生命周期

### 这里的“发布”不是上线，而是生成一个稳定快照

```
     创建
       │
       ▼
    ┌──────┐
    │ DRAFT │ ←── 正在修改、调试、本地试跑
    │ 草稿  │     可通过 --draft 执行草稿版本
    └──┬───┘
       │ 发布（冻结当前稳定版本）
       ▼
  ┌───────────┐
  │ PUBLISHED │ ←── 给别人复用、给 Agent 调用、
  │ 已发布    │     给定时任务执行的稳定快照
  └──┬────┬──┘
     │    │
     │    └── 归档 (ARCHIVED)
     │
     └── 丢弃草稿 → 回到上次稳定版本
```

### 脚本作用域

| 作用域 | 说明 | 可编辑 |
|--------|------|--------|
| PERSONAL | 个人创建 | 完全控制 |
| REPOSITORY | 从仓库安装 | 只读，可 Fork |

## 多入口执行 — 同一脚本，多种调用方式

### 管理台

```
打开脚本库 → 找到脚本 → 点击「运行」→ 填入参数 → 查看结果
```

### CLI

```bash
actiondock script run hello-groovy --name alice --json
```

### REST API

```bash
curl -X POST http://localhost:5177/api/scripts/hello-groovy/execute \
  -H 'Content-Type: application/json' \
  -d '{"input": {"name": "alice"}, "mode": "SYNC"}'
```

### 定时任务

```
触发中心 → 定时触发 → 选择脚本 → 设置 Cron → 自动执行
```

### Webhook 事件

```
外部系统 → POST /api/event-sources/{id}/events → 标准化 → 过滤 → 执行脚本
```

### AI Agent

```
Agent 推理 → 决定调用脚本工具 → plugins.invoke("actiondock-ai", "agentRun", ...) → 脚本执行
```

## 脚本能力快速提供给外部大模型

### 过去的常见做法

```text
写脚本
  └── 手动整理调用方式
       └── 手写 Skill / Prompt
            └── 反复调试给外部模型用
```

### ActionDock 里的更直接路径

```text
写脚本
  └── 命令页自动生成 Skill 示例
       └── 进入 Skill 发布 / 安装流程
            └── 外部大模型直接复用
```

### `Skill 示例` 里实际带什么

- `scriptId`、执行模式、当前输入来源
- 当前页面对应的 CLI 调用命令
- 可回退的 HTTP 调用命令
- `inputSchema` / `outputSchema`
- 当前输入示例和复杂参数传递约定

### 这页要强调的结论

- 脚本不只是平台内部 Agent 的工具
- 脚本也可以很快包装成外部大模型可直接使用的 Skill
- 重点不是多一份文档，而是少一轮手写 Skill 和手工对齐命令

## 什么脚本最适合先接入

### 优先接入这几类

1. **高频手工脚本** — 你或团队成员经常重复执行
2. **参数复杂脚本** — 每次都要查 README 或翻源码
3. **多入口脚本** — 同时想从 CLI、UI、AI 或定时任务调用
4. **团队共享脚本** — 已经开始发给别人用
5. **AI 增强脚本** — 希望作为 Tool 暴露给 Agent

### 不建议第一批接入的脚本

- 一次性实验脚本
- 输入输出还没稳定的探索型逻辑
- 强依赖临时本地交互环境的代码

## 脚本执行架构

```
调用入口                    应用服务层              引擎抽象层
┌────────┐                ┌───────────┐          ┌──────────────┐
│REST API│──┐             │           │          │ ScriptEngine  │
├────────┤  │             │  Script   │          │   接口        │
│  CLI   │──┼────────────→│Invocation │─────────→│              │
├────────┤  │             │  Service  │          ├──────────────┤
│UI 手动 │──┤             │           │          │ GroovyEngine │
├────────┤  │             │           │          │ (JVM 内编译)  │
│Agent   │──┘             └───────────┘          ├──────────────┤
└────────┘                                       │ PythonEngine │
                                                 │ (子进程执行)  │
                                                 └──────────────┘
                                                        │
                                                 ┌──────┴──────┐
                                                 │ 上下文注入    │
                                                 │ plugins      │
                                                 │ scripts      │
                                                 │ state        │
                                                 │ config       │
                                                 │ log          │
                                                 └─────────────┘
```

- **Groovy**: JVM 内编译执行，编译结果缓存
- **Python**: 子进程执行，通过 stdin/stderr 桥接协议通信
- **跨语言透明调用**: Groovy 调 Python、Python 调 Groovy 均可

## 脚本运行时 API

### 调用其他脚本（跨语言透明）

```groovy
// Groovy
def result = scripts.invoke("target-script", [param1: "value1"])
```

```python
# Python
result = scripts.invoke("target-script", {"param1": "value1"})
```

### 调用插件

```groovy
def result = plugins.invoke("my-plugin", "action-name", [key: "value"])
```

### 调用 AI

```groovy
plugins.invoke("actiondock-ai", "chat", [
    modelProfileId: "my-model",
    messages: [[role: "user", content: "Hello"]]
])
```

### 共享状态（CAS 乐观锁）

```groovy
state.get("ns", "key")
state.put("ns", "key", [data: "value"])
state.cas("ns", "key", [data: "new"], 3)   // version=3 时才成功
```

### 支持的 AI 能力

| 能力 | 说明 |
|------|------|
| `chat` | 多轮对话补全 |
| `structured` | 按 Schema 生成结构化 JSON |
| `embed` | 文本向量化 |

### 脚本自动注册为 AI 工具

所有已发布的 `TOOL` 类型脚本自动注册为 AI 可调用工具，Agent 可自主决定何时调用哪个脚本。

### 这和 Skill 的关系

- Skill 可以给 Agent 补上下文、规则、步骤
- ActionDock 给 Agent 提供真正可调用的工具
- 两者结合时，AI 既知道“该做什么”，也真的“有东西可做”

## 治理能力

### 对本地工具来说，治理的重点是“共享与沉淀”

### 配置值管理

- 全局键值存储，用于 API Key、连接字符串等
- **Secret 标记** — 敏感值在 UI 和日志中自动脱敏
- **引用分析** — 追踪哪些脚本、模型引用了某个配置值
- **模板语法** — 支持 `${config.key}` 占位符引用

### 共享状态

- `namespace + key` 组织，命名空间隔离
- `version` + CAS 乐观锁，并发安全
- `expiresAt` 自动过期
- 完整审计追踪（最后写入脚本、执行 ID）

### 访问令牌

- 格式: `adk_{id}_{secret}`
- SHA-256 哈希存储，恒定时间比较
- **开放模式**: 未配置令牌时所有请求免认证
- 创建后仅显示一次，妥善保存

### 数据备份与恢复

- 14 种数据类型完整备份
- 支持 Secret 值包含/排除
- 恢复前预览分析（创建/覆盖/跳过计数）

## CLI 工具

### 一键安装，开箱即用

```bash
npm install -g actiondock
actiondock server     # 启动服务
```

### CLI 不是补充入口，而是完整自动化接口

- 覆盖脚本创建、修改、校验、发布、执行
- 覆盖插件、仓库、事件、状态、配置、服务管理
- 适合人工使用，也为后面的模型辅助开发提供接口面

### Schema 驱动的 CLI 参数

```bash
# inputSchema 自动展平为 flag
actiondock script run my-script --name alice --age 30 --json
```

### 对脚本开发最关键的命令闭环

```bash
actiondock script create --script-id my-script --name "My Script" --source-file ./script.groovy
actiondock script patch my-script --source-file ./script.groovy
actiondock script validate my-script
actiondock script publish my-script
actiondock script run my-script --name alice --json
```

### 这一页先讲到哪里为止

- 先强调 CLI 模块完整，覆盖脚本生命周期
- 先强调 Schema 会直接驱动命令参数
- 先不要在这里展开“模型怎么写脚本”，把它留到下一页

### 命令覆盖

| 类别 | 命令 |
|------|------|
| 脚本 | `list` `create` `patch` `publish` `run` `schema` |
| 插件 | `list` `install` `invoke` `config` |
| 调度 | `list` `create` `enable` `disable` |
| 事件 | `event-source` `event-trigger` `event-record` |
| 状态 | `state get/put/cas/list/delete` |
| 配置 | `config set/show/clear` |
| 服务 | `server` `desktop` `service install/start/stop` |

## 高级能力：让大模型辅助编写脚本

### 这是进阶玩法，不是第一天必须使用

- 前提是目标、边界、验收标准由人先给清楚
- 模型负责补源码、补 Schema、跑 CLI 流程
- 人负责审核结果，而不是把高风险动作全放开

### 它依赖的不是“魔法”，而是现成接口

```text
目标描述
  └── 模型生成脚本源码和 Schema
       └── 通过 CLI 执行 create / patch / validate / publish / run
            └── 人确认结果是否满足预期
```

### 这件事为什么成立

- CLI 已覆盖脚本创建到发布的关键链路
- Schema 可以让模型更稳定地补输入输出契约
- Skill 可以补充步骤、约束和命令使用约定

### 这页的定位

- 这是高级自动化开发能力
- 不是 adoption 主线的第一亮点
- 它建立在前面已经讲过的 Schema、Skill 示例和 CLI 之上

## 技术亮点

### 1. 端口与适配器架构

核心领域层不依赖任何具体实现（Spring、JPA、AI Provider），所有外部依赖通过端口接口解耦。

### 2. Python 子进程桥接

Python 引擎通过 stdin/stderr 桥接协议实现与 Java 主进程的通信，支持脚本间调用、插件调用和状态操作，无需嵌入 Python 解释器。

### 3. 脚本自动注册为 AI 工具

已发布的 `TOOL` 类型脚本自动注册到 ToolRegistry，Agent 可自主发现和调用，无需额外配置。

### 4. 事件处理管道

标准化 → 过滤 → 幂等 → 输入映射，四阶段管道确保事件处理的可靠性和灵活性。

### 5. CAS 乐观锁

共享状态的版本号 + Compare-And-Swap 机制，保证并发场景下的数据一致性。

### 6. 开放模式 + 安全模式

无令牌时自动开放（开发友好），配置令牌后自动启用认证。

## 适用边界

### 它不是零成本，也不是万能

- 需要维护者补 `inputSchema` / `outputSchema` / 描述，这是一笔治理成本
- 不是所有脚本都值得资产化，一次性脚本没必要强行接入
- 如果要做团队共享，仍然需要基本的仓库和发布规范
- AI 工具调用应该从最小权限开始，不要一开始就给高风险能力

### 更适合它的，是这类问题

- 反复运行的本地工具
- 希望被多人复用的脚本
- 想统一成 CLI / UI / Agent 入口的能力
- 希望长期沉淀为团队工具库的自动化逻辑
