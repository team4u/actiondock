# 工作流

按这个顺序执行，除非用户明确只要求其中一部分。批大小、状态值、正式产物路径和 checkpoint 文件名统一以 `knowledge-contract.json` 为准。

## 1. 判断模式并建立写入边界

- 确认 `repoPath` 存在，且看起来是代码仓库。
- 检查知识库入口、`docs/`、已有报告、已有人工文档和可恢复的临时目录。
- 自动判断 `init` 或 `refresh`；如果用户明确指定，以用户输入为准。
- 先建立保护边界：发现阶段只读仓库，草稿阶段只写临时目录，正式文档只在汇总阶段写入。

## 2. 建立发现基线

- 从构建文件、依赖清单、README、配置文件、OpenAPI、DDL、ORM、日志样例和 CI 建立项目画像。
- 识别语言、框架、模块边界、入口点、运行方式、关键流程入口、核心表、状态枚举、事务边界、外部依赖、任务和管理操作。
- 如果用户提供 `evidenceFiles`，读取这些补充材料并提取其中对当前仓库有价值的事实、术语、排查片段、DDL 说明或生成偏好。
- 不要求把 `evidenceFiles` 统一整理成固定结构；如当前轮需要，可在 `.knowledge-tmp/` 留自由格式摘要，记录来源、吸收去向和跳过原因，供本轮写作辅助。
- `refresh` 时先读取已有知识库，建立“现有结论 -> 证据路径”的映射，并标记过期、冲突、缺失和新增事实。
- 把发现结果写入 `.knowledge-tmp/`：项目画像、证据映射、流程候选、表清单、工具上下文线索、诊断线索，以及当前轮需要的外部证据摘要。

## 3. 激活分析域

- 读取 `scan-domains.md`，只激活有证据支持的域。
- 先形成候选索引，再决定每个候选项是生成正文、跳过还是进入人工审查。
- 域激活后只读取对应模板文件；不要因为某个大域激活就加载全部模板。
- `evidenceFiles` 只能补充现有证据面：术语、工具上下文、排查片段、DDL 说明和生成偏好；与代码事实冲突时，以代码为准并记录冲突。
- 当流程或表的规模达到契约中的 batch 阈值时，进入自动分批模式。

## 4. 起草域草稿

- 领域写作单元只读发现结果，只向 `.knowledge-tmp/domain-drafts/` 写草稿。
- 每份草稿先建立结构，再补证据，最后写解释性正文；不要把扫描清单直接当最终文档。
- 草稿必须以最终文档粒度组织：一条端到端流程一篇、一张表一篇、一个诊断场景一节。
- 发现清单和外部证据摘要只能被吸收到正式索引、正文或报告中；正式文档不得链接临时文件。

## 5. 自动分批循环

- 当契约阈值触发 batch 模式时，先生成批次计划和 checkpoint，再循环处理。
- 每轮只选择当前批次的 `pending` 项，按域加载最小模板集，写当前批草稿并更新 checkpoint。
- 单批证据不足或质量不达标时标记为 `skipped` 或 `needs_review`，写明原因并继续后续批次。
- `resume=true` 且 checkpoint 存在时，从未完成批次继续，不重复已完成批次；重新读取 `evidenceFiles`，不要把上轮临时摘要当作事实来源。

## 6. 合并和正式写入

- `init` 生成第一版入口、报告和有证据支撑的 `docs/`。
- `refresh` 只更新受影响文档，标记过期结论、冲突证据、新增流程、新增字段和语义缺口。
- 汇总时统一术语、去重交叉引用、补齐入口到流程/数据/诊断/运维的阅读链路。
- Refresh 模式直接更新受影响的文档，不保留历史版本。
- 报告必须按来源说明外部证据的处理结果：吸收到哪些文档、哪些内容被跳过、跳过或冲突的原因是什么。

## 7. 语义校验与收尾

- 读取 `quality-gates.md` 做语义审查：事实、证据、深度、SQL 可用性、诊断可操作性、刷新影响面和外部证据吸收情况。
- 汇总后人工检查入口链接、占位符、临时目录引用、覆盖统计、按来源的外部证据记录，以及明显浅文档。
- 只有在确认没有待续跑、`in_progress` 或 `needs_review` 批次时，才删除 `.knowledge-tmp/`；否则保留并在报告中说明原因。
